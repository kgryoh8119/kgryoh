# スムシティ 設計資料（Phase 1）

最終構想（指示書 2〜3 章の全モード・全分野）のうち、今回実装するのは **Phase 1：架空の市の市長モード** だけです。
本書は実装前に決めた設計で、実装後に数値と制限を追記しています。

## 1. 全体構成と技術選定

| 層 | 場所 | 役割 | 依存 |
|---|---|---|---|
| ゲーム状態・計算 | `src/sim/` | 唯一の正である `GameState` と月次計算、操作、予測、保存 | なし（DOM・Three.js を参照しない） |
| 設定データ | `src/sim/config.ts` `src/sim/events.ts` | 係数、施設定義、政策、イベント | なし |
| 描画 | `src/render/` | `GameState` を読んで 3D を作るだけ。状態を書き換えない | Three.js |
| UI | `src/ui/` | 画面部品。操作は `dispatch(action)` 経由 | DOM |
| 進行管理 | `src/game.ts` | 時間の積算、計画案（下書き）、保存 | sim |

技術選定の理由：

- **TypeScript + Three.js（r186）+ Vite**。既存プロジェクトはなく新規の Web 版を作れる環境だったため、指示書の候補どおり。Node 22 で動作確認。
- **React は採用しない**。Phase 1 の画面は「月 1 回＋操作時に描き直すパネル」が中心で、状態は `GameState` に一本化している。フレームワークなしの方が配布物が小さく、単一 HTML にまとめやすい。画面が増える Phase 2 以降で再検討する。
- **サーバーなし**。保存はブラウザの localStorage と JSON ファイルの書き出し・読み込み。
- **建物モデルは全てコード生成**（外部アセットなし）。屋根・窓・入口・植栽・看板を部品として組み、建物全体を少数のメッシュに結合して描画回数を抑える。
- テストは Vitest。sim 層は DOM に依存しないので Node 上でそのまま回せる。

## 2. データ構造

```
GameState ──┬─ road[] / roadAge[] / zone[] / occ[]   （44×44 タイルの格子。Parcel に相当）
            ├─ buildings[] : Building                  （民間の住宅・店舗と公共施設を同じ型で持つ）
            │     ├─ 住宅 : units, hh[5]               （世帯コホート：建物ごとの世帯類型別世帯数）
            │     ├─ 店舗 : revenue, lossStreak        （Business）
            │     └─ 施設 : staff, staffTarget, effCap, used, age, status（Facility / ConstructionProject）
            ├─ policies{}                              （Policy：有効かどうかと開始月）
            ├─ modifiers[] / scheduled[]               （期限つき効果と遅延効果）
            ├─ events{ active[], cooldown{}, log[] }   （EventInstance）
            ├─ loans[] / ledger[]                      （BudgetLedger：月次の歳入歳出内訳）
            ├─ stats / history[]                       （直近の集計と月次履歴）
            ├─ voices[]                                （住民の声。実際の不足から毎月作り直す）
            └─ rng, month, term, mode, pledges         （乱数状態、時間、任期、公約）
MapDef（地形・水域・保全林・地区区分）はシードから再生成し、GameState には含めない。
District は MapDef の地区番号（駅前／本町／丘陵台／西新町）で、集計は毎月 Building から作る。
RoadNode＝道路タイル、RoadEdge＝上下左右の隣接。ForecastScenario は GameState の複製に対する実行条件。
SaveData = { format, version, savedAt, state }。
```

- **世帯モデル**：全員を個別エージェントにせず、住宅 1 棟ごとに 5 類型（単身・夫婦・子育て（未就学）・子育て（就学）・高齢）の世帯数を実数で持つ集約モデル。人口・児童数・就業者数は「世帯数 × 類型ごとの平均人数」で求める。地区別・類型別の値は毎月この建物別データから集計する。
- **画面の通行人・車は演出**で、台数は交通量に比例させるが人口とは別物。画面にもそう表示する。
- **所有と権限**：施設定義に `owner`（市／民間／県／鉄道事業者／国）と `authority`（直接建設／誘致・補助／協議のみ）を持たせる。市が直接建てられるのは保育園・小学校校舎・公園・消防署・水道施設・ごみ収集拠点。私立保育園は補助と協議、店舗と住宅は用途指定と誘致、駅・交番・診療所・国道は協議対象で操作不可。小学校の教職員は県が配置する扱い（市は人件費を負担しない）。

## 3. 単位と定義

| 値 | 単位 | 種別 |
|---|---|---|
| 金額 | 万円 | `cash` は残高（累積）、収支は月額 |
| 世帯・人口 | 世帯・人 | 残高。内部は実数、表示は四捨五入 |
| 保育需要 | 人 | 未就学児 × 利用希望率。月ごとに再計算 |
| 設計容量 | 施設ごとの単位（人・世帯） | 建物の定員 |
| 実効容量 | 同上 | 設計容量 × 職員充足率 × 老朽係数 × 更新中係数。道路未接続なら 0 |
| 利用量 | 同上 | その月に実際に割り当てた量 |
| 交通量 | 台/時（朝の通勤時間帯） | 月ごとに再計算 |
| 混雑率 | 交通量 ÷ 道路容量 | 1.0 で容量いっぱい |
| 老朽度 | 0〜100 | 累積。60 から能力低下、100 で使用停止 |
| 満足度 | 0〜1（画面は %） | 月ごとに再計算 |
| 距離 | 道路タイル数（1 タイル 30m） | 道路網上の経路長。直線距離は使わない |

価格・税率・人口係数は全てゲーム用の仮定で、`src/sim/config.ts` の `P` で変更できる。

## 4. 月次の計算順序

1 か月 = 1 ステップ。`stepMonth()` は次の順で進む。前半は「先月の状況への反応」、最後に状態から導ける値を全部作り直す。

1. 予約されていた遅延効果の実行、期限切れ効果の削除
2. 工事・更新工事の進行（公共・民間）、完成処理
3. 職員の採用・退職（目標人数へ向けて、職種ごとの採用上限つき）
4. 世帯の変化：類型の遷移（年齢）→ 転出 → 転入（空き住戸と満足度で配分。入れなかった分は「住宅待ち」）
5. 店舗：赤字が続けば閉店、空き商業区画は見込み売上が採算を超えれば開業
6. 民間住宅開発：道路接続・水道余力・住宅需要を見て着工
7. 老朽化（施設・道路）
8. 財政：歳入・歳出を台帳に記録、借入返済、残高不足なら一時借入
9. イベント判定（予測実行時は発生させない）
10. 月を進める → 任期末なら評価と選挙
11. **再計算**（`recompute()`）：道路接続 → 施設の実効容量 → 保育・学校・公園・消防・水道・ごみの割当 → 商圏と売上 → 交通配分と混雑 → 満足度 → 住民の声 → 集計

`recompute()` は金銭・乱数・人口を変えない。道路や施設を操作した直後にも呼び、地図レイヤーとプレビューをすぐ更新する。

依存関係（→ は「影響する」）：

```
道路網 → 接続・経路距離 → 施設の実効容量と到達範囲 → 保育・学校・公園・消防の水準 ┐
住宅・世帯 → 保育/学校需要、買物需要、通勤交通 → 店舗売上・混雑 ─────────────────┼→ 満足度 → 転出入 → 住宅需要 → 民間開発
職員・老朽度 → 実効容量                                                          ┘        └→ 税収・支持
```

## 5. 状態遷移（施設）

```
[着工：全額を着工時に支出] → construction ──工期満了→ operating ⇄ suspended（休止：維持費 30%、職員 0）
                                  │                      │  └ 老朽度 100 → suspended（使用停止）
                                  └ 中止（未施工分の 50% 返金） └ 更新を指示（更新費を支出）→ renewing ──満了→ operating（老朽度 0）
operating / suspended → 撤去（撤去費を支出、区画を解放。借入は残る）
```

- 建設費・更新費は**着工時に 1 回だけ**支出する（支出時点の統一）。
- 維持費は operating で 100%、renewing で 60%、suspended で 30%、construction で 0。老朽度 60 超で割増。
- 民間建物は construction → operating →（閉店・解体で削除）。

## 6. 境界条件

- 現金は負にならない。操作は残高不足なら拒否。月次赤字で不足した分は自動で「一時借入」（高金利）になり、財政評価を下げる。
- 世帯数・職員数・容量・老朽度は 0 以上に丸める。転入は空き住戸数を超えない。
- 読み込み時に形式・版・配列長・建物と区画の対応・数値の有限性を検査し、矛盾があれば理由を表示して読み込まない。

## 7. 予測

`forecast()` は `GameState` を複製し、複製側で `stepMonth` を回す。本番の状態・現金・乱数は変えない。
転入の強さを 楽観 ×1.2／基準 ×1.0／慎重 ×0.8 に変えた 3 本を、「現在のまま」と「計画案」の 2 通りで計算する。
計画案は「試算モード」で作る：本番の複製に対して通常どおり建設や政策変更を行い、操作列を記録する。採用すれば同じ操作列を本番に適用し、破棄すれば何も残らない。
予測中はイベントを発生させない（その旨を画面に明記）。

## 9. 簡略化している点（Phase 1）

- 道路は直線の格子のみ。斜面は緩い丘まで（1 タイルの高低差 3.5m 以下）。橋・トンネル・曲線は未対応。
- 上下水道は拠点の処理能力と道路接続だけ。管路は扱わない。下水は水道施設に含める。
- ごみは収集拠点の処理能力だけ。焼却は市外の広域施設に委託している扱い（費用は維持費に含む）。
- 雇用は市内の職（店舗・施設）と、駅・国道経由の市外通勤の合算。失業は個別に追わない。
- 交通は朝の通勤時間帯 1 時点を 3 回に分けて最短時間経路へ配分する。信号や右左折は扱わない。混雑の指標は市道だけで見る（国道は国の管理）。
- 税・移転収入は実制度ではなく「住民税相当」「固定資産税相当」「事業課税相当」「基礎的移転収入」というゲーム独自の近似。
- 選挙は満足度・公約・財政からの得票率計算のみ。議会、対立候補の政策はなし。
- 駅は市外との接続拠点としてのみ扱う。交番・診療所は景観と権限説明のためだけに置いてあり、計算には影響しない。

## 10. 実装後の追記

- 月次計算は 1 か月あたり 5〜8 ms。予測（60 か月 × 3 本）は約 2 秒かかるため、画面を止めないよう数か月ごとに制御を返しながら計算する。
- 街の 3D は 6×6 区画の塊ごとに結合メッシュを作り、変わった塊だけ作り直す。建物全体を 1 メッシュにする当初案は、作り直しに 0.5 秒かかったためやめた。
- 道路は 2.5m の升目で車道・歩道を塗り分け、地形の高さに沿わせている。
- 保存はブラウザ内とテキストの書き出しの 2 通り。公開ページの枠内ではファイルのダウンロードが効かないため。
- 何もしないと落選し、課題に対応すると当選できるよう、係数を自動プレイ（`scripts/balance.ts`）で調整した。
